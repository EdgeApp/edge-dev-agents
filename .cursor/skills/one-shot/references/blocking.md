Governs the blocked completion, in any phase; the core step map cross-cutting row `True-blocker` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="yolo-true-blockers">Even in `--yolo`, STILL stop for a true-blocker — by taking the BLOCKED COMPLETION defined below — when any of these apply: (a) destructive op with no recovery path (force push outside a PR branch, git history rewrite on shared branch, file deletion outside scratch/build dirs); (b) user-only credential needed (2FA, password, OAuth re-auth, signing key passphrase); (c) no defensible default exists (genuine ambiguity that could flip task outcome wholesale); (d) risk of overwriting unstaged user work (dirty working tree on a non-agent-created branch). (e) an operator ruling is pending: a non-operator human's comment or description edit postdates the operator's last word, per task-review `operator-final-say` (`asana-get-context.sh` reports `LAST_HUMAN_WORD: other` and `require-plan-before-developing.sh` blocks Developing); the `--reason` names each open item by author, and the ONE agent comment that precedes the block lists each proposal with the plan's chosen default so the operator can rule in one line. A BLOCK IS A COMPLETION ("blocked completion"): a true-blocker ends the run at `Complete` with the `blocked` flag set — never at a bare `blocked = Yes` with a phase status. ONE gated write does both: `~/.config/agent-watcher/update-status.sh <gid> Complete --blocked yes --reason "<the precise blocker>"` — the `--reason` is mandatory. WHY Complete (owns the rationale; other rules reference it): a task sitting blocked mid-orch keeps its session+slot parked on the watchdog's special blocked lane, and if that session dies before a sweep (machine restart, tmux server death) the slot/sim leak with nothing left to reclaim them — the completion sweep is session-driven and never visits a gid with no session. A blocked completion retires through the SAME deterministic teardown as every other Complete (session retired, sim+slot+Metro freed, report attached), and re-engagement is the SAME single path: the operator resolves the blocker, clears `blocked`, and sets `Pending` (`followup-reopens-status`). A PreToolUse gate (`require-completion-judgment.sh`) sends the `--reason` to the COMPLETION JUDGE (`~/.cursor/skills/completion-judge`: a fresh headless Opus that reads only the evidence bundle and rules against the true-blocker taxonomy; you never run it and cannot argue with it); if it denies, you are NOT blocked — do exactly what each failed item's `what_to_do` says (swap-to-fund, build the missing maestro flow per `build-the-test-harness`, link the unmerged dep, attempt the action) and CONTINUE. A funds/provider block also requires a real attempt logged via `~/.config/agent-watcher/log-attempt.sh` (result `loss:`/`failed:`/`blocked:`) — predicting a wall is not hitting it. A blocked completion attaches the run report like any other `Complete` (per `report-as-attachment`), with the blocker named in the report; ALSO post ONE brief one-line Asana comment naming the blocker BEFORE the attachment (comments-before-attachment watermark rule) so a human knows what input is needed to unblock. CARVE-OUT to (a): spending SANCTIONED test funds — the sim-testing playbook roster accounts, at the playbook's amounts — is NEVER condition (a), no matter how new or unvetted the code path is. A real test swap through prototype plugin code is the prescribed verification (build-and-test `gui-dependency-integration`, `test-drives-the-real-action`), not a destructive op. Do not invoke (a) to skip a funded in-app test. The ONLY funds-related true-blocker is an OBSERVED loss: an attempted swap/send that failed AND lost principal. Fees/slippage never count (budgeted at $15 equivalent per run, per the sim-testing playbook), and a loss can only be established by an actual attempt, never predicted.</rule>
</rules>
