Governs the PR-watch phase of `/one-shot` (`agent_status = Reviewing`); the core step map row `6. PR watch` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="pr-watch-bounded-poll">Every step-6 wait is ONE call: `~/.cursor/skills/one-shot/scripts/watch-pr.sh --pr <num> --task-gid <gid>`. The script owns the budget arithmetic — it computes a single 30-minute deadline per task on first call and bounds each subsequent watch by the remaining budget. Exit contract: 0 = green, with the final `RESULT:` line distinguishing `green` (everything passed), `green-travis-pending` (all but the slow Travis check passed — proceed, per finalize-gate's travis-pending carve-out, and state Travis's status in the report), and `green-wip-preserve` (all passed except the wip-guard check, red only because preserved `fixup!` commits sit on the branch during an active review — proceed, NEVER squash to clear it; it goes green when pr-finalize-fixups legitimately squashes at finalize); 1 = a check failed, Travis included (fix, amend, re-run); 7 = `RESULT: continue`, the per-call cap hit with checks still pending: re-invoke the same command immediately (not a failure; the remaining budget carries over, and it is still the same one wait); 75/124 = budget exhausted (take the blocked-completion exit per `yolo-true-blockers`). Never hand-roll a polling loop; never spawn anything to wait (`never-self-respawn`). Exit 76 (`RESULT: no-checks`) is neither green nor budget exhaustion: the PR has nothing posting checks, so re-watching cannot help.</rule>
<rule id="bugbot-in-watch">Treat the configured reviewer bots (`reviewer-bots`) as checks inside the step-6 watch — the watch blocks until their check-runs complete, and each force-push re-triggers them on the new HEAD. A reviewer-bot check-run that completes `NEUTRAL` (not `SUCCESS`) posted findings and is NOT clean — `gh pr checks`/`watch-pr.sh` will exit 0 on it (neutral is a non-failure), so you MUST separately check each reviewer bot's conclusion and review state, not rely on the watch's exit code (see `finalize-gate`). For `cursor[bot]` invoke `/bugbot` to examine and FIX findings whenever its check-run is `NEUTRAL` or it left a `COMMENTED` review, even though the watch passed; address other allowlisted bots inline. Do NOT arm bugbot's recurring cron (`CronDelete` it if armed) — the watch does the waiting. Reviewers can't reach clean within budget → blocked completion per `yolo-true-blockers` (report attached like any `Complete`).</rule>
<rule id="reviewer-bots">The automated PR reviewers to gate on live in asana-config `.watcher.reviewer_bots` (default `["cursor[bot]", "cursor"]` — Cursor's bot posts as `cursor[bot]` over REST and `cursor` over GraphQL; both are listed, but the load-bearing match is `__typename == "Bot"` per `finalize-gate`, not the literal logins). The step-6 watch and `finalize-gate` wait on EVERY one (its check-run completed-clean on HEAD + no unresolved threads from it). Additionally — semantic catch — if a check-run or PR review comes from an author that LOOKS like a bot (a `[bot]` login, or an automated/non-human reviewer) but is NOT in the allowlist: do not silently ignore it. If it posted actionable findings, treat the PR as not-green until addressed, and record "new automated reviewer `<login>` detected — consider adding to `.watcher.reviewer_bots`" under the run report's **Skill Gaps / Follow-ups & Risks** section. This keeps the allowlist authoritative while surfacing new reviewers for you to confirm.</rule>
</rules>

<step id="6" name="PR watch (gate to Complete)">
Keep agent_status=Reviewing (set in step 5; the PR is up and under external review by CI, reviewer bots, and humans). Wait for external green signals before marking `Complete`. Status stays at `Reviewing` throughout. Every wait is one `watch-pr.sh` call per `pr-watch-bounded-poll`; the script owns the 30-minute budget.

1. **CI checks**: run `~/.cursor/skills/one-shot/scripts/watch-pr.sh --pr <pr-num> --task-gid <gid>`. When it returns —
   - exit 0 (all pass) → CI is green
   - exit 1 (a check failed) → read the failing job's log via `gh run view --log-failed`, apply a fix, then commit it by the strategy for this phase (pre-first-human-review on an owned PR: amend + force-push per `pr-watch-loop-amend-pattern`; after a human review or on a PR you do not own: the fixup model per `followup-reopens-status` / `non-owner-pr-completion`), then re-run `watch-pr.sh`. A WIP-blocker check that fails only because of your `fixup!` commits on a non-owned PR is expected, not a "check failed" to fix (`non-owner-pr-completion`)
   - exit 7 (`RESULT: continue`) → re-run the same `watch-pr.sh` command immediately
   - exit 75 or 124 (budget exhausted) → take the 30-min exit below
   - exit 76 (`RESULT: no-checks`) → the PR has NO checks at all: nothing will ever go green. Do not re-watch it. Name the repo's missing CI in the report's Finalize Gate and finish the run on the evidence you have.
2. **One watch covers CI and the bots** (2026-09-11, replacing the two-phase draft/ready gate): the PR is READY from creation, so the CI checks, Travis and every `reviewer-bots` check-run land on the same HEAD and ONE `watch-pr.sh` call blocks until all of them complete, per `bugbot-in-watch`. There is no ready-flip step and no `[skip travis]` tag to strip. A Travis that finishes RED is a normal check-fail fix cycle. If a PR shows ZERO checks, `watch-pr.sh` exits 76 (`RESULT: no-checks`) after 5 minutes rather than burning the budget: that is a CI-configuration problem on the repo, so name it in the report's Finalize Gate and do NOT keep waiting on it.
3. **Re-test after a fix (semantic)**: after applying ANY fix in this loop, reason about whether the change could affect behavior that `/build-and-test` covers. If it could (logic/UI/build changes) AND this is a `--yolo` run, re-run `/build-and-test` before re-entering the watch. The trigger is RUNTIME REACH, NOT DIFF SIZE: a fix confined to lint, comments, markdown/docs, or pure config the app never executes skips the re-test and the report says which fixes were inert; a fix touching ANY code the app runs re-drives at build-and-test `test-on-sim-by-default`'s bar (the real action to terminal success), and "small diff", "obvious fix" and "static analysis says it is fine" are the excuses that rule exists to refuse, never carve-outs here. Don't blindly re-test every fix; don't skip it for real behavioral changes. When a re-test produced NEW proof screenshots, attach them via `pr-attach-screenshots.sh` so the evidence on the PR matches the current HEAD. The fix moved the head sha, so that attach retires the previous frames and the script will ask for a disposition on each (carry forward what the fix left true, retire what it invalidated) per pr-create `evidence-dispositions`.

Exit conditions:
- **All green** (per `finalize-gate`: CI checks pass + every `reviewer-bots` check-run completed-clean on HEAD + no unresolved threads from any of them): proceed to step 7.
- **30 min wall-clock elapsed**: take the blocked completion (`yolo-true-blockers`) with the one-line comment summarizing what was still red.
- **True-blocker hit during a fix attempt**: take the blocked completion per `yolo-true-blockers`.

Honor `yolo-stop-at-pr` strictly: never merge, never tag, never deploy DURING the watch. The only mutations here are force-pushes to the PR's own branch. After green, step 7's routing may sanction a land (`land-on-approval`, via /pr-land) or a `test-*` cheese push (`cheese-build-on-green`) — those are the only post-green exceptions.
</step>
