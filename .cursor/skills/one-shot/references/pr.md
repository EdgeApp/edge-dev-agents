Governs the PR-creation phase of `/one-shot` (`agent_status = Reviewing`); the core step map row `5. PR creation` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="attach-prs-by-default">ATTACH each PR to its Asana task by default — pass `--asana-attach` (and `--asana-task <gid>`) to `/pr-create`; this produces a real GitHub-widget link (`ASANA_GITHUB_SECRET` is exported into agent sessions; `asana-task-update` degrades to a warning if it's absent). A comment is a FALLBACK, never the goal: if you only commented the PR URL, the attach was skipped — check the secret. Do NOT pass `--asana-assign` (see `pr-create`'s `no-reviewer-assignment`).</rule>
<rule id="task-gid-for-pr-body-link">When a task GID is available (from Asana URL input or explicit `--asana-task` flag), always pass `--asana-task <gid>` to `/pr-create` so it injects the Asana link into the PR body. This is the canonical Asana ↔ PR link consumed by `pr-land` and other downstream skills.</rule>
<rule id="pr-body-owned-by-pr-create">Do not draft alternate PR markdown formats inside this workflow. `/pr-create` owns PR body generation and template compliance.</rule>
<rule id="pr-watch-loop-amend-pattern">SCOPE: this amend-fold applies ONLY before any human has reviewed the PR AND only on a PR you own. In that window (the step-6 automated watch iterating on CI failures / reviewer-bot findings on your own fresh commits), fold each fix into the existing commit(s) with `git commit --amend --no-edit` + `git push --force-with-lease` so the PR's history stays a single clean commit (or the minimum logically-distinct set the implementation needed) and the human's first review sees tidy history. Once `pr-address.sh review-mode` reports `preserve` (the only definition of "a human has reviewed": bots and your own replies under the operator's login do not count), OR on a PR you do NOT own, DO NOT amend — switch to the fixup-commit model per `followup-reopens-status` (which delegates to `/pr-address`). In `autosquash` mode a followup's rewrite of the branch's own published lines is still a FOLD (fixup into the commit that owns the surface, per `/im` step 3 item 5), never a standalone commit; the push gate rejects the latter. Never use `--force` without `--with-lease` — if the branch has been touched by someone else, that's a true-blocker (take the blocked completion per `yolo-true-blockers`).</rule>
<rule id="non-owner-pr-completion">When the PR author is NOT you (`currentUser != prAuthor` in `/pr-address` `fetch`; the operator is directing work on someone else's PR): push `fixup!` commits and reply to threads, but per `/pr-address`'s `non-owner-reply-only` never rewrite the owner's commit, never autosquash, and never resolve HUMAN threads (reviewer-bot threads you addressed may be resolved). The fixups stay on top for the OWNER to squash at merge. This changes `finalize-gate` two ways: (a) a WIP-blocker CI check (e.g. `block-wip-pr`) that fails SOLELY because of your legitimate `fixup!` commits is NOT a completion blocker — it clears only when the owner squashes, which is their action; treat "green except that one WIP-blocker" as green. (b) The terminal state is NOT a merge (`land-on-approval` does not apply): reach green-except-WIP with every reviewer-bot thread addressed and the change retested, then set `Complete` — the PR is handed back to the owner for their re-review and squash-merge. The same "ready-for-re-review = Complete after the retest flow" holds for an OWNED PR followup that addressed human review comments (green + threads resolved + retested), the only difference being who re-reviews.</rule>
</rules>

<step id="5" name="PR phase">
Set agent_status=Reviewing. Run `/pr-create` so the PR opens READY for review (operator policy 2026-09-11, replacing the 2026-07-31 bugbot-credit gate and the 2026-08-06 Travis queue gate): a DRAFT PR posts no reviewer-bot check-runs, and with `[skip travis]` on HEAD it gets no Travis check either, so a draft can sit at ZERO checks with nothing for the step-6 watch to gate on (the BTC/LTC/XMR explorer run, 2026-09-11, waited its whole budget on an accountbased PR in exactly that state). Ready-from-creation means CI, Travis and the bots all post on the same HEAD. The cost is deliberate: every later fix force-push re-triggers all of them. Pass `--asana-task <gid>` (so the Asana link is embedded in the PR body, per `task-gid-for-pr-body-link`) AND `--asana-attach` (attach the PR to the task via the GitHub widget, per `attach-prs-by-default`), and never pass `--asana-assign`. If the run produced PRs in MORE THAN ONE repo, instead build the subtask-per-PR structure per `multi-repo-subtasks` (and `dep-pr-draft-vs-bump` for dependency PRs). The step-4 test run saved proof screenshots (`/tmp/agent-proof-<gid>-NN-<slug>.png`, per build-and-test's `proof-screenshots-for-pr`); `/pr-create` step 4b attaches them to the PR as the test-evidence comment — verify that happened (every gui-tested PR should carry its screenshots).

Task GID source priority: (1) explicit `--asana-task <gid>`; (2) Asana task URL from step 1; (3) chat context from prior steps.
</step>
