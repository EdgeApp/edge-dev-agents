Governs the land/build routing that runs at finalize-green, before the report (`agent_status = Reviewing`); the core step map row `7.0 Land / cheese routing` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="land-on-approval">At finalize-green (and ONLY there: `finalize-gate` green means every reviewer-bot thread is already resolved, so auto-merge can never arm over an unaddressed automated review), decide landability before Complete: `landable = (the PR carries a human APPROVED review; ANY point in its history counts, it need not be on the current HEAD, since comment-fix commits after the approval were already addressed and re-tested per `followup-reopens-status` (4)) OR (~/.cursor/skills/asana-force-land.sh <gid> prints land-approved, the operator's no-review override for trivial changes)`. If landable: FIRST release the sim with `~/.config/agent-watcher/lane-release.sh --task-gid <gid> --land`. A landing needs no sim, re-fires that skip planning reach this point without `lane-release-after-plan` having run, and any sim-dependent re-testing is already DONE, so the release is always safe here. Then run `/pr-land` passing the TASK URL, never the bare PR number: pr-land walks the task + subtasks to assemble the full multi-repo set, which is what triggers its dep ordering (defer-gui: merge dep → publish → upgrade-dep on develop → only then rebase+merge the GUI PR). pr-land owns the entire land contract and you do not return here until it is DONE to its last step: rebase, conflict resolution, verify, arming GitHub auto-merge, staging cherry-pick per `build-field-routing`, the dep release chain (`land-dep-publish-boundary`), and its FINAL Asana handoff (`--set-board-state "QA Verification" --unassign`, pr-land `asana-last`), which `agent_status = Complete` does NOT cover, since that is a different field. Never raw `gh pr merge`, and Force Land authority is bounded by `force-land-is-not-a-ci-bypass`. If pr-land reports `blocked` (changes requested) or `unsupported`, fall back to stop-at-PR and say why in the report. When the land armed or merged, SKIP `cheese-build-on-green` (CI builds wherever the landing happened) and set Complete with the report stating `merged` or `auto-merge armed, waiting on CI`. Not landable → stop at PR per `yolo-stop-at-pr`.</rule>
<rule id="force-land-is-not-a-ci-bypass">Force Land is never a CI bypass: when branch protection demands an approving review that does not exist, pr-land's watch reports `BLOCKED_ON_REVIEW` only after every check on HEAD is green with zero pending, and only that verdict plus Force Land authority permits the admin merge past exactly the review requirement (pr-land `force-land-review-bypass`). Pending or red checks always wait, and pr-land re-checks PR comments immediately before the admin merge: new feedback is addressed (fix, reply, resolve, re-testing behavioral changes) exactly as on an approved landing, and a substantive objection parks the PR instead of landing.</rule>
<rule id="land-dep-publish-boundary">FOR A DEP-REPO DELIVERABLE (a GUI-dependency package), `merged` alone is NOT complete: the release chain (publish, then the GUI dep bump) is part of the land per pr-land `publish-gating`. Deferring the publish as "a separately-coordinated release step" is a false complete. A dep publish inside the land needs the operator's npm 2FA (pr-land `npm-publish-auth`), a user-only interaction: land everything landable before the publish boundary, deliver the publish AUTH_URL via push notification (never Slack) and wait ONLY as long as the publish script's own link-remint budget; if the operator has not tapped by then (or no notification channel exists) take the blocked completion naming the auth need (`Complete --blocked yes`, `yolo-true-blockers` (b)). The publish is resumable via pr-land's idempotent path on the next `Pending` re-arm; do not skip the publish or dismiss the remaining PRs. So Complete comes only after the chain is DONE, or ended at that operator-auth boundary as a blocked completion.</rule>
<rule id="cheese-build-on-green">AFTER `finalize-gate` reports green and BEFORE attaching the run report or setting `Complete` (Complete triggers session retirement, so post-Complete work races the watchdog sweep): classify the task's Build field with `~/.cursor/skills/asana-build-field.sh <gid> --kind`, which prints `staging`, `cheese` or `none`. ORDER: decide landability per `land-on-approval` FIRST. An approved/force-landed PR LANDS and the cheese push is skipped entirely (the Build field is ignored for landable runs; CI builds where the landing happened); only a non-landable green run kicks the cheese. On `cheese`, kick the build via /cheese: target branch `test-<value>` (the value from the same script without `--kind`), source ref = the task's PR head branch. `--kind` is the only sanctioned test: NEVER match the value against a list of cheese names you carry, because the roster is operator data on the Asana field and it grows, so a remembered list silently skips an owed build. CHEESE IS A POINTER, NOT A WORKSPACE (cheese:`pointer-not-workspace`): all work lives on the PR branch and is already pushed there; the cheese op is ONLY a hard-reset of `test-<value>` to that pushed head + force-push, and CI auto-builds on `test-*` pushes. Never commit to or develop on a `test-*` branch. DEP PINS: when the gui deliverable requires unpublished dep PRs, pins are REQUIRED per cheese:`orch-pins-required` (the task's own dep PRs, each pinned at its PR head; carve-outs and mechanics live there); single-repo tasks stay plain pointer resets. Followups need no special casing: a re-engaged run that ends green re-runs the same reset, so the test branch tracks the amended head. `staging` routes through /pr-land (not this rule); `none` means no build routing. This `test-*` force-push is sanctioned and is NOT a ship action under `yolo-stop-at-pr`. Record the push (branch, source sha) in the run report's Summary.</rule>
</rules>
