Governs the land/build routing that runs at finalize-green, before the report (`agent_status = Reviewing`); the core step map row `7.0 Land / cheese routing` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="land-on-approval">At finalize-green (and ONLY there — `finalize-gate` green means every reviewer-bot thread is already resolved, so auto-merge can never arm over an unaddressed automated review), decide landability before Complete: `landable = (the PR carries a human APPROVED review — ANY point in its history counts, it need not be on the current HEAD; comment-fix commits after the approval are fine because this run already addressed the threads and re-tested behavioral changes per `followup-reopens-status` (4)) OR (~/.cursor/skills/asana-force-land.sh <gid> prints land-approved — the operator's no-review override for trivial changes)`. If landable: FIRST release the sim — `~/.config/agent-watcher/lane-release.sh --task-gid <gid> --land` (a landing needs no sim, and this decision point is reachable on re-fires that skip planning entirely, where `lane-release-after-plan` never ran: the 2026-07-14 Banxa lands held sims 2h+ through pure landing work, 1h45m of it just waiting on the land mutex) — any sim-dependent re-testing per `followup-reopens-status` (4) is already DONE by the time landability is decided, so the release is always safe here. Then run `/pr-land` passing the TASK URL, never the bare PR number — pr-land walks the task + subtasks to assemble the full multi-repo set, which is what triggers its dep ordering (defer-gui: merge dep → publish → upgrade-dep on develop → only then rebase+merge the GUI PR). pr-land owns the entire land contract and you do not return here until it is DONE to its last step: rebase, conflict resolution, verify, arming GitHub auto-merge, staging cherry-pick per `build-field-routing`, the dep release chain per `publish-gating`, and its FINAL Asana handoff (`--set-board-state "QA Verification" --unassign`, pr-land `asana-last`) — which `agent_status = Complete` does NOT cover, since that is a different field. Never raw `gh pr merge`. Force Land is never a CI bypass: when branch protection demands an approving review that does not exist, pr-land's watch reports `BLOCKED_ON_REVIEW` only after every check on HEAD is green with zero pending, and only that verdict plus Force Land authority permits the admin merge past exactly the review requirement (pr-land `force-land-review-bypass`) — pending or red checks always wait, and pr-land re-checks PR comments immediately before the admin merge: new feedback is addressed (fix, reply, resolve, re-testing behavioral changes) exactly as on an approved landing, and a substantive objection parks the PR instead of landing. A dep publish inside the land needs the operator's npm 2FA (pr-land `npm-publish-auth`): that is a user-only interaction — land everything landable before the publish boundary, deliver the publish AUTH_URL via push notification (never Slack) and wait ONLY as long as the publish script's own link-remint budget; if the operator has not tapped by then (or no notification channel exists) take the blocked completion naming the auth need (per `yolo-true-blockers` (b)) — the publish is resumable via pr-land's idempotent path on the next `Pending` re-arm; do not skip the publish or dismiss the remaining PRs. If pr-land reports `blocked` (changes requested) or `unsupported`, fall back to stop-at-PR and say why in the report. When the land armed or merged, SKIP `cheese-build-on-green` (CI builds wherever the landing happened) and set Complete with the report stating `merged` or `auto-merge armed, waiting on CI`. FOR A DEP-REPO DELIVERABLE (a GUI-dependency package), `merged` alone is NOT complete: the release chain — publish, then the GUI dep-bump PR — is part of the land per pr-land `publish-gating`, so Complete only after that chain is DONE or ended at the operator-auth boundary as a blocked completion (publish AUTH_URL delivered via push notification, link budget expired, `Complete --blocked yes` naming the auth need). Deferring the publish as "a separately-coordinated release step" is the false-complete shape the 2026-07-24 NYM land produced. Not landable → stop at PR per `yolo-stop-at-pr`, exactly as before (a fresh task's first run is naturally not landable — this branch fires in practice on followups, after a human has approved).</rule>
<rule id="cheese-build-on-green">AFTER `finalize-gate` reports green and BEFORE attaching the run report or setting `Complete` (Complete triggers session retirement, so post-Complete work races the watchdog sweep): classify the task's Build field — `~/.cursor/skills/asana-build-field.sh <gid> --kind`, which prints `staging`, `cheese` or `none`. On `cheese`, kick the build via /cheese: target branch `test-<value>` (the value from the same script without `--kind`), source ref = the task's PR head branch. NEVER match the value against a list of cheese names you carry: the roster is operator data on the Asana field and it grows (Kraft, Colby, String, Parm, Swiss and Paneer were all added after the original four), so a hardcoded allowlist silently skips an owed build. `String` read as a placeholder and skipped a cheese on task 1218291556240193, 2026-09-09; `--kind` is the only sanctioned test. CHEESE IS A POINTER, NOT A WORKSPACE (cheese:`pointer-not-workspace`): all work lives on the PR branch and is already pushed there; the cheese op is ONLY a hard-reset of `test-<value>` to that pushed head + force-push — CI auto-builds on `test-*` pushes. Never commit to or develop on a `test-*` branch. ORDER: decide landability per `land-on-approval` FIRST — an approved/force-landed PR LANDS and the cheese push is skipped entirely (the Build field is ignored for landable runs; CI builds where the landing happened). Only a non-landable green run kicks the cheese. DEP PINS: when the gui deliverable requires unpublished dep PRs, pins are REQUIRED per cheese:`orch-pins-required` (the task's own dep PRs, each pinned at its PR head; carve-outs and mechanics live there); single-repo tasks stay plain pointer resets. Followups need no special casing: a re-engaged run that ends green re-runs the same reset, so the test branch tracks the amended head. `staging` routes through /pr-land (not this rule); `none` means no build routing. SKIP the cheese push entirely when this run is LANDING the PR per `land-on-approval` — CI builds wherever the landing happened, so a cheese build would be redundant. This `test-*` force-push is sanctioned and is NOT a ship action under `yolo-stop-at-pr`. Record the push (branch, source sha) in the run report's Summary.</rule>
</rules>
