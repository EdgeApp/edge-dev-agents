<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="report-as-attachment">Do NOT post progress, narrative, or status comments to the Asana task during the run (no per-phase updates, no "agent paused" essays). Run state is conveyed by the `agent_status`/`blocked` field transitions, nothing else. Attach the structured run-report DOC **only at `Complete`** — the true end of the run. A block IS a completion (`yolo-true-blockers`: `Complete --blocked yes` in one write), so a blocked completion attaches the report exactly like any other `Complete`, with the blocker named in it; the one-line comment naming the blocker posts BEFORE the attachment per the watermark ordering below. There is no non-terminal blocked state anymore — a run never sits at `blocked = Yes` with a phase status. At `Complete`: produce exactly ONE structured run report from the template `~/.cursor/skills/one-shot/templates/agent-run-report.md`. RE-READ THE TEMPLATE FILE (Read/cat) immediately before writing EVERY report — including followup reports N compactions later. A prior read never carries: the template's inline contract (section set, style rules like no-reversibility-annotations) does not survive compaction, and writing "from remembered shape" is how the Reversible. trailer regressed 5x into a followup report on 2026-07-09 while the one-line summary of the rule sat in fresh context. The `require-clean-run-report.sh` gate lints the report at attach, so a skipped re-read gets caught there and costs a rewrite. Fill the frontmatter and every section (including the infra-capture fields: `sim_udid` from `$AGENT_SIM_UDID`, `metro_port` from `$AGENT_METRO_PORT`, `slot_index` from `node ~/.config/agent-watcher/lib/slots.js get --task-gid <gid>`; these let post-hoc evals verify resource accounting after the slot is released), using `_None observed._` for empty ones (never omit a section), keep it dense — and attach it via `asana-task-update.sh --task <gid> --attach-file <path> --attach-name agent-run-report.md`; the attach gate renames it to `<N>-agent-run-report.md` (N = report ordinal on the task), so never number it yourself. COMMENTS COME BEFORE THE ATTACHMENT: the report attachment's `created_at` IS the followup-scope WATERMARK (`followup-scope-is-the-deliverable`), so any comment posted after it is invisible to the next run's scope check and to the next report's own watermark arithmetic. Post every comment this run owes — the completion comment below, a block note, a correction to an earlier note — FIRST, then attach the report. A comment you find yourself wanting to add after attaching is a signal you attached too early: post it, then re-attach the report so the watermark lands last. COMPLETION COMMENT IS EXCEPTION-ONLY: the attachment story is itself the completion signal, so post a comment ONLY when there is information the operator cannot get from the surfaces they already see, and then only these three kinds, as short bullets (one per item, never a prose block): (1) review findings this run REJECTED as false positives (one bullet each: finding + why rejected); (2) testing gaps — what was NOT verified and why (mirror `verify_blockers`), naming any 🪓 hack-forced frames per build-and-test `hack-verify-visual-changes`; (3) a one-line "auto-landed via Force Land: <PR>" note when the run landed with NO human approval (silent when the land followed an explicit approval). Nothing else: no "run report attached", no "screenshots attached", no "not merged, human decision", no phase narration — all derivable from the feed, the PR, and the fields. No exceptions → NO comment. If no task GID is available (ad-hoc text task), skip the attachment and report only in chat. The chat-facing summary is unaffected. FRONTMATTER HONESTY: if `verified` is `not-run` or `partial`, `verify_blockers` MUST be non-empty and name why (`precondition` | `harness` | `code` | `task-drafting`); an empty `verify_blockers` paired with `verified: not-run`/`partial` is a silent downgrade-finalize that `require-concession-validation` now intercepts at `Complete` (per `yolo-no-silent-downgrade`), so fill it truthfully or reach `verified: pass` first. `verified: n/a` is valid ONLY on a Task deliverable (/task-run) whose segment had no runtime surface to exercise; the Testing section then names the evidence that stands in for a drive. A PR deliverable never uses it.</rule>
<rule id="description-current-state">At `Complete`, when what this run DELIVERED differs from what the task description's operator prose still says (evolved scope, superseded requirements, shipped PRs the prose predates), refresh the agent-maintained CURRENT STATE section at the BOTTOM of the description. NEVER edit the operator's prose above the delimiter — this section is the ONLY part of a description an orch run may write. Write it with `~/.cursor/skills/asana-task-update/scripts/asana-task-update.sh --task <gid> --set-current-state <file>`, whose body file carries the BULLETS ONLY: the delimiter, the strip-and-replace of any previous section, the preservation of the operator prose above it, and the authorship markers are all the script's (asana-task-update `current-state-owns-the-tail`). Never hand-roll the notes PUT. Body contents: when the task has a TDD, open with the label line `Technical Design Document:` followed by the doc's `TDD_BRANCH_URL` on its own line (bare URL — Asana notes render plain text, not markdown). Then 2-6 tight bullets: what the task has evolved into, what already shipped (PR links); bullets reference "the design doc linked above" rather than repeating the URL. Skip when the description still accurately describes the delivered scope — an unchanged first run needs no section. WHY (owns it; `inject-run-context.sh` references this rule): a long-lived task's description goes stale while the real spec scatters across comments and reports; fresh-spawned followups and humans reading the board both anchor on the description, so the description itself must carry its own supersession.</rule>
