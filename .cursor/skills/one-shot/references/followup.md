Governs a re-engaged run: a resume on a task you already finished, or operator scope added since the last run report; the core step map cross-cutting row `Followup` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="followup-reopens-status">A finished task (`agent_status = Complete`/`Archived`) is RE-ENGAGED by the operator setting it back to `Pending` — the SINGLE re-engage signal. The watcher then RESUMES your prior session (your full prior conversation restored, on a FRESH slot with a working sim + Metro) when a transcript exists, or fresh-spawns a never-run task. So when you find yourself resumed on a task you previously finished, you are continuing a FOLLOWUP: your prior context is intact, the status is already off `Complete` (the resume moved it), and your resources are live. Do NOT move the status yourself, and do NOT expect dead resources (the watcher's resume re-provisions a fresh slot, unlike the old in-place un-retire). Apply: (1) FOLLOWUP SCOPE — the operator's comments since your last run-report ARE the deliverable, per `followup-scope-is-the-deliverable`; (2) WORKTREE — if your prior worktree was pruned and the task has an OPEN PR, re-provision on that PR's branch via `~/.config/agent-watcher/setup-task-workspace.sh --task-gid <gid> --repo <name> --existing-branch <pr-head-branch>`, never a fresh branch off develop (that orphans the PR's work); (3) STALE-PRIOR-HISTORY GUARD — your prior report/conclusions are historical context, NOT current truth about the environment: re-verify every env/tooling claim (debug flags, dev servers, build paths, provider availability) before working around it ("X didn't work" before is not evidence X fails now); (4) PR-COMMENT-ADDRESS — if the task's open PR has any UNRESOLVED review threads (human OR reviewer-bot), addressing them IS part of this run's deliverable, with NO separate `/pr-address` invocation: reuse `/pr-address`'s reply-then-resolve workflow inline (read `~/.cursor/skills/pr-address/SKILL.md`) — for each unresolved thread apply the fix, reply stating what changed, then resolve the thread. COMMIT STRATEGY — a followup addressing review threads always postdates a review, so use `/pr-address`'s FIXUP-COMMIT model, NOT the pre-review amend of `pr-watch-loop-amend-pattern`: one `fixup! <target-headline>` per target commit per human-review turn (`one-fixup-per-target-per-turn`), condensing all of this turn's fixes — reviewer-bot churn included — into it, and let `pr-finalize-fixups.sh` own squash-vs-preserve (the policy lives in that script's `review-mode` oracle; raw autosquash is hook-blocked while it says preserve, and a red wip-guard check in that state is `green-wip-preserve`, not a failure to clear). A genuinely NEW or unrelated scope addition is a new logical commit, not a fixup. Flow the phase statuses as you go: `Developing` (applying fixes) → `Testing` (re-run `/build-and-test`, since a comment fix can change behavior, per step 6 point 3) → `Reviewing` (re-push, re-gate). Both human and bot threads must be replied-and-resolved before green; one-shot is the continuous monitor that owns finalize, so IT — never `/pr-address`, per pr-address `never-sets-completion` — sets `Complete`. Then re-finalize per `finalize-gate`. Phase statuses (`Developing`/`Reviewing`/`Testing`) are progress indicators YOU set as you go, NOT re-engagement triggers — setting a finished task to a phase status does nothing (the watchdog's old un-retire-on-phase-status was removed 2026-06-25); `Pending` is how a finished task comes back.</rule>
<rule id="followup-scope-is-the-deliverable">A resume is a FOLLOWUP when the operator added new scope to the task AFTER the last `agent-run-report` was attached. That attachment is the "agent reported done here" WATERMARK: any operator comment NEWER than it — or, if the task has never had a report attached, EVERY operator comment — is scope this run has NOT yet discharged. BEFORE finalizing, ENUMERATE the operator comments since that watermark with the LIVE fetch `~/.config/agent-watcher/check-followup-scope.sh --task-gid <gid>` (it fetches the task's comments + attachments, computes the watermark from the latest `agent-run-report*.md` attachment's `created_at`, prints every newer comment, and writes the marker the Complete gate checks). RECALLED CONTEXT NEVER SATISFIES THIS: every watcher resume compacts your session from a summary built BEFORE the followup comment existed (the resume menu's "Resume from summary" runs /compact), so "the newest comment is my own Complete note" remembered from context is exactly the stale claim that re-Completed past the UTXO followup — only the script's live output counts, and the `require-followup-scope-on-complete.sh` PreToolUse gate blocks `update-status.sh <gid> Complete` without a fresh check. READ EVERY comment; ACT on the parts addressed to you. An operator comment is an ask for this run only where it tells the run what to do or asks the run something; a clause that hands work or a question to someone else (QA, a reviewer, a teammate, whether or not it @mentions them) is theirs: context for what happens next, never a deliverable, never something to report as undelivered, never something to wait on unless told to wait. Decide by who is being told to act; a name or @mention is a signal, not the test (the completion judge applies the same reading, rubric "who a comment is for"). A clause you cannot place is yours: do it, and say in the report that you read it as addressed to you. Treat each concrete ask for you (added workstreams, new acceptance criteria, "also do X") as THIS run's PRIMARY deliverable — NOT the task's pre-existing open PR. Re-anchoring on the already-open PR, verifying/finishing it, and setting `Complete` while that newer scope is deferred is a FALSE COMPLETE: it advances the report watermark PAST asks it never addressed, so they silently vanish. DELIVER it: do the new scope to its DoD like any task and ship its PR(s) — to the parent, or, for work in ANOTHER repo, to a per-repo subtask per `multi-repo-subtasks`. Subtasks are UNWATCHED containers (no `agent_status`, never spawned by the watcher — the orch tracks ONLY the parent); a subtask exists to hold one extra-repo PR or split-out context, NOT to offload scope to a separate run. So you cannot discharge the new scope by "creating a subtask for it" — only by DELIVERING the work. If a newer ask is genuinely too large to finish in this run, that is established by ATTEMPTING it, NEVER by predicting from the code: you may surface it as unfinished ONLY after a GENUINE logged attempt (link the WIP/unpublished dep via updot/`--existing-branch`, pin its tarball, build, spike the integration) hit a concrete wall recorded via `log-attempt.sh` (`failed:`/`blocked:` with the real error). A predicted "too big / WIP-only / would require finishing an unmerged migration" without that logged spike is a PREMATURE descope, and the completion judge denies it (`unmerged dependency` / `too-large-unattempted` in its concession taxonomy). Having actually hit the wall: ship what you can, then SURFACE the remainder explicitly in one Asana comment that names exactly what is undone and why (so the operator can spin it into its own top-level task), and do NOT set the parent `Complete`. HARD GATE: do NOT attach the run-report and set the PARENT `Complete` while any operator ask newer than the prior report is neither DELIVERED (its work shipped, PR attached to the parent or a per-repo subtask) nor explicitly surfaced-as-unfinished with the parent left non-`Complete`. Finishing the pre-existing deliverable is fine and may earn its own PR, but it does NOT discharge the newer scope. DISTINGUISH from a same-deliverable resume (`followup-reopens-status`): a resume that merely FINISHES the SAME blocked deliverable with NO operator comment newer than the last report legitimately ends at `Complete`; the trigger is operator scope added since the watermark. "Documented as follow-ups" buried in a report line, or a placeholder subtask with no delivered work, is precisely the false-complete this forbids.</rule>
</rules>
