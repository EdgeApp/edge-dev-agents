Governs the finalize gate and the move to `agent_status = Complete`; the core step map row `7.2 Finalize gate and Complete` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="finalize-gate">The single definition of "done", owned by the CONTINUOUS monitor (one-shot's step 6→7, or `/bugbot` run standalone with a task GID to finish a task after a blocker cleared) and never by a one-off: `/pr-address` NEVER sets Complete, because automated reviews can land after it finishes. The gate is evaluated on HEAD of EVERY PR this run created or pushed to, in every repo: enumerate them before declaring green (the run's own PR list, cross-checked with `gh pr list --author @me` per touched repo) and gate on EACH. Gating only the oldest PR while a newer one's CI still runs (a second-repo PR, a late dep bump) is a completion-honesty violation. Green = CI passes AND every reviewer bot reviewed HEAD clean (`reviewer-bot-coverage`) AND no review thread is unresolved (`review-threads-block`). CI: every check passes (`gh pr checks <pr>`), read from `watch-pr.sh`'s `RESULT:` line. Exactly three non-passing states count as green: (a) `green-wip-preserve`, a WIP-blocker check red SOLELY from legitimate `fixup!` commits while the squash oracle says preserve (an active reviewer on a PR you own, or ANY PR you do not own per `non-owner-pr-completion`); `watch-pr.sh` classifies it from the same `review-mode` oracle pr-finalize-fixups uses. (b) `green-travis-pending`, on a STOP-AT-PR run only: a Travis check still QUEUED/RUNNING does not block, since it only re-runs what the run already passed locally; state Travis's status in the run report's Finalize Gate checklist. A FAILED Travis always blocks, and a LANDING run gets no such allowance: `land-on-approval` → pr-land requires full green including Travis. (c) `green-dep-sanctioned`, CI red only because a dependency is unpublished, on a PR carrying the `awaiting-dep-publish` sanction (`dep-blocked-pr-vs-bump`). The sanction excuses those CI checks and neither of the other two conditions; in the Finalize Gate leave the CI box UNCHECKED, naming the excused checks and the awaited `<pkg>@<version>`. When green AND a task GID with an `agent_status` field exists → set `agent_status=Complete` (`~/.config/agent-watcher/update-status.sh <gid> Complete`).</rule>
<rule id="reviewer-bot-coverage">The `finalize-gate` condition on reviewer bots: every `reviewer-bots` check-run completed-clean on HEAD, where clean means conclusion `SUCCESS` ONLY. NEUTRAL IS NOT CLEAN: a `NEUTRAL` conclusion, or a bot REVIEW in state `COMMENTED`/`CHANGES_REQUESTED`, means the bot POSTED FINDINGS without hard-failing; examine and address/resolve them (cursor → `/bugbot`, others inline) before green. `gh pr checks` and the watch exit 0 on a neutral check, so never treat their green exit as covering a reviewer bot. REVIEWER UNAVAILABLE IS NOT REVIEWER CLEAN, AND IS NOT A BLOCKER: `reviewer-unavailable:<name>(<why>)` on `watch-pr.sh`'s RESULT line means that reviewer did not review HEAD (it posted no check-run, or posted one and SKIPPED it, which is what running out of quota looks like), so a `skipped` reviewer check counts as coverage for NOTHING, and waiting cannot change it. Proceed to Complete and record it as an UNCHECKED Finalize Gate box naming the reviewer and the reason, never as a checked reviewer-clean box. THAT BOX IS THE WHOLE RECORD: mention the outage nowhere else, in no report section, comment or session narration (`require-clean-run-report.sh` and the Asana comment hook reject the extra mentions).</rule>
<rule id="review-threads-block">The `finalize-gate` condition on review threads: zero unresolved. On a PR you own, an `isResolved:false` thread from ANY author is not-green, a human reviewer's exactly like a bot's and whether or not it predates this run: reply and resolve each (`/bugbot` for `cursor[bot]`) before Complete. On a PR you do not own, human threads are reply-only and non-blocking per `non-owner-pr-completion`. READ THREADS THE RIGHT WAY: from `check-followup-scope.sh` or the shared `pr-address.sh fetch` (or `pr-land-comments.sh`), which query `reviewThreads` and detect bots by `__typename == "Bot"`. Never substitute `gh pr view --json reviews,comments`: bot findings post as INLINE review threads, which it does not surface. Never hand-roll a literal-login comparison either: GraphQL strips the `[bot]` suffix, so Cursor's reviewers appear as `cursor` there and `cursor[bot]` over REST (`reviewer-bots` lists both logins as a fallback; `__typename` is the primary match).</rule>
<rule id="on-complete-actions">The task's `agent_on_complete` text field is the operator asking, in advance, for the run's LAST action: one line per action, plain imperatives ("assign the task to X", "remove rule X from skill Y", "post in #channel that Z shipped", "set field F on task T"), sometimes with a condition line. It runs once, immediately before `update-status.sh <gid> Complete`, on every orch run shape (one-shot and task-run alike; blocked completions included), never earlier. This step is the field's only reader: session-start context and `check-followup-scope.sh` leave it out, so it never reaches a run as scope. Execute each line exactly as if the operator had typed it in chat right now, through whatever skill or script owns that kind of work (`asana-task-update.sh` for a task change, /slack for a message, /author + rubric-drift + /convention-sync for an orch change, ...). The kinds are open; do not refuse a line for being an unlisted kind. The field is operator-written (agents never set it) and is authorization on its own: ask nothing. A false condition means skip, with the reason. Record every line through `~/.cursor/skills/one-shot/scripts/asana-on-complete-actions.sh --mark` (done, skipped with reason, failed with reason, or `note` for a condition or remark) so a re-engaged run repeats only what is still pending. A failed action never blocks or reverses Complete: name it in the run report's Follow-ups & Risks and leave it pending.</rule>
<rule id="yolo-stop-at-pr">In `--yolo` mode, NEVER merge the PR, tag a release, deploy, publish a package, or perform any other "land/ship" action. The agent's terminal action is reaching `agent_status = Complete` after the watch loop reports all-green. Merging is the human's decision. Force-pushing to the PR's own branch (to apply review/CI fixes) is allowed and expected. CARVE-OUT, a LAND/MERGE task: when the task's EXPLICIT deliverable is to land or merge an EXISTING PR (signals: name/description like "land", "merge", "finish landing <X> PR", or it names a specific open PR to merge with no new code expected), the merge IS the deliverable. Do NOT stop-at-PR and do NOT block on this rule; delegate to `/pr-land`. SECOND CARVE-OUT: landing an APPROVED feature PR at finalize-green, per `land-on-approval`. Everything else (a feature task with an unapproved PR and no Force Land field) stops at PR. If genuinely ambiguous whether the task wants a merge, treat it as a normal feature task and stop at PR.</rule>
<rule id="yolo-no-silent-downgrade">Finalizing (opening a PR or setting `Complete`) while the prescribed in-app drive did NOT reach success is itself a CONCESSION (a DOWNGRADE), gated exactly like a formal block. The SAME gate (`require-completion-judgment.sh`) sends EVERY `/pr-create` and `update-status.sh Complete`, first segment or followup, wall or no wall, to the completion judge, whose J2 (testing depth and funding) and J5 (deferral validity, the concession taxonomy) dimensions catch a finalize whose latest attempt-log entry is a wall (`failed:`/`loss:`/`blocked:`), whose `/tmp/agent-test-blocker-<gid>.md` note exists, or whose attempt-log is simply EMPTY: you verified a weaker way, skipped the in-app drive, or bailed on a crash. A deny means the downgrade is NOT earned: do each failed item's `what_to_do` (apply the sim-testing playbook's documented continue-workaround for a known gotcha, swap-to-fund, build the missing harness) and reach the real success. The gated direct-verification fallback is legitimate ONLY with a GENUINE funded attempt logged (`log-attempt.sh` result `failed:`/`loss:`/`blocked:`) AND no remaining continue-workaround. Do not pre-empt the gate by skipping the attempt; ATTEMPT, log, then let the verdict rule. The judge also rules J1 asks-satisfied on every Complete: each ask in the task description and every operator comment since the report watermark must be delivered or explicitly surfaced with a logged attempt; a narrower delivery than asked (one token when "multiple" was asked) is a deny.</rule>
</rules>

<step id="7" name="Report (attach run report, then Complete)">
Build the run report and attach it, THEN mark Complete. Per `report-as-attachment`, this attachment (not comments) is how the run is documented.

0. Land + build routing FIRST (before the report, so the outcome is recorded in it):
   a. Landability per `land-on-approval`: check the PR for a human APPROVED review (`gh pr view <pr> --json reviews`) and run `~/.cursor/skills/asana-force-land.sh <gid>`. Landable → `/pr-land <task-url>` (task URL, never the bare PR), then skip (b).
   b. Not landing: cheese check per `cheese-build-on-green` — `~/.cursor/skills/asana-build-field.sh <gid>`; on a cheese value, run /cheese (`test-<value>` ← PR head; dep pins as that rule requires). Then continue.
1. Copy `~/.cursor/skills/one-shot/templates/agent-run-report.md` to a scratch path named with BOTH the GID and the task short-name: `/tmp/agent-run-report-<gid>-<short-name>.md`. Fill the frontmatter — set `agent_session_uuid` from `$AGENT_SESSION_UUID` (the orchestration session that ran this), plus `outcome: complete`, `verified`, `verify_blockers`, repo/branch/pr, started/ended, `skills_used` — and every section. Use `_None observed._` for empty sections; keep it dense (bullets, signal over prose). Map content to sections:
   - phases that ran (`/asana-plan`, `/im`, `/pr-create`, `/build-and-test`) + watch-loop iteration counts → **Summary**.
   - the `/build-and-test` run as RUN EVIDENCE (do not leave thin — this is the visibility surface): the real action driven to terminal success (or the exact step it stopped at + why), method (static checks tsc/jest/eslint/verify-repo, naming failures and new cases only, sim build flavor, maestro flow path + MCP-explore vs yaml-proof, any `/debugger` use), environment (sim UDID/slot, roster account + any `config.json` switch, funding asset+amount + any swap-to-fund, provider forced + reverted), proof-screenshot paths + confirmation they are PR-attached, any gated direct-verification fallback, and what stayed unverified (mirror `verify_blockers`) → **Testing**. HACK-FORCED FRAMES ARE DECLARED, NOT BURIED: for every `HACKED`-named screenshot (build-and-test `hack-verify-visual-changes`), open the Testing section's screenshot list with a 🪓 line naming the file, the exact hack, that it was reverted with a clean `git status`, and what the frame does NOT prove (the trigger). A hack-forced frame listed like an organic one is a completion-honesty violation.
   - in `--yolo`, every auto-deferred decision (question, default chosen) → **Decisions** (flag only IRREVERSIBLE choices, per the template).
   - build/test/debug learnings → **Dev Notes & Gotchas** (inline-tagged). Harness friction → **Orchestration**. Skill defects → **Skill Gaps**.
2. Post the completion comment FIRST, per `completion-comment-exception-only` (bulleted false positives / testing gaps / Force-Land note, or NO comment at all; reviewer-bot availability is never a bullet, per `reviewer-bot-coverage`) — the attachment in step 2b sets the watermark (`comments-before-attachment`).
2b. THEN attach the report: `asana-task-update.sh --task <gid> --attach-file /tmp/agent-run-report-<gid>-<short-name>.md --attach-name agent-run-report.md` (the attach gate renames it to `<N>-agent-run-report.md`). Skip both if no task GID (ad-hoc task) and report in chat only.
3. Set the `tested` field to the method(s) actually performed (per `set-tested-field`): `~/.config/agent-watcher/set-tested.sh <gid> <Option ...>`. Skip the call on a followup segment that rule exempts (no shipped code changed, no new verification owed).
3b. Operator's last action, per `on-complete-actions`: `~/.cursor/skills/one-shot/scripts/asana-on-complete-actions.sh --task <gid> --pending` (empty output = nothing owed; the JSON mode without `--pending` prints every line, conditions included). Carry out each pending line, then record all outcomes in ONE call: `asana-on-complete-actions.sh --task <gid> --mark <id>=done --mark <id>=skipped:"<why>" --mark <id>=failed:"<what went wrong>" --mark <id>=note:"condition, not an action"`. Exit `2` = bad id or state (re-list, retry), `1` = Asana error.
4. Set agent_status=Complete — ONLY after `finalize-gate` reports all-green.
5. Return a short chat summary + PR URL + phases ran.

Per `report-as-attachment`, the run-report doc is attached at `Complete` — including a blocked completion, which attaches it like any other `Complete` with the blocker named (one-line blocker comment first, then the attachment).
</step>
