Governs the finalize gate and the move to `agent_status = Complete`; the core step map row `7.2 Finalize gate and Complete` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="finalize-gate">The single definition of "done", owned by the CONTINUOUS monitor — never a one-off. Green = all CI checks pass (`gh pr checks <pr>`; EXCEPT a WIP-blocker check red SOLELY from legitimate `fixup!` commits while the squash oracle says preserve — an active reviewer on a PR you own, or ANY PR you do not own (`non-owner-pr-completion`) — `watch-pr.sh` classifies this from the same `review-mode` oracle pr-finalize-fixups uses and reports `green-wip-preserve`; and EXCEPT the TRAVIS-PENDING CARVE-OUT (2026-07-24): on a STOP-AT-PR run, a Travis check that is still QUEUED/RUNNING does not block green — Travis runs 9-13 min but queues 40-90 min under contention, and it only re-runs what the run already passed locally — so `watch-pr.sh` exits 0 with `RESULT: green-travis-pending` and Complete may proceed, with Travis's status stated in the run report's Finalize Gate checklist. A FAILED Travis always blocks (red is signal, queued is not), and LANDING runs get no carve-out: `land-on-approval` → pr-land requires full green including Travis — auto-merge waits on required checks and `BLOCKED_ON_REVIEW` requires zero pending) AND every `reviewer-bots` check-run completed-clean on HEAD AND no unresolved threads from any of them — evaluated over the PRIMARY PR(s) only. CHECK UNRESOLVED THREADS THE RIGHT WAY: bot findings post as INLINE review threads, which `gh pr view --json reviews,comments` does NOT surface — using it makes the gate blind and is how a live cursor[bot] thread slipped past a Complete. Query review threads via graphql, fetching the author's `__typename` (NOT just `login`): `gh api graphql -f query='{ repository(owner:"O",name:"R"){ pullRequest(number:N){ reviewThreads(first:100){ nodes{ isResolved isOutdated comments(first:1){ nodes{ author{ login __typename } } } } } } } }'` and treat any `isResolved:false` thread from ANY author as not-green on a PR you own — a human reviewer's open thread blocks exactly like a bot's (the Maya re-fire re-Completed past an OPEN human thread on 2026-07-29 because this check was worded bot-only; `check-followup-scope.sh` now surfaces owned-PR unresolved threads and the Complete gate blocks on them). On a non-owned PR, human threads are reply-only and non-blocking per `non-owner-pr-completion`; the author-type distinction (`__typename`) still matters for the bot-specific NEUTRAL semantics below. MATCH BOTS BY `__typename == "Bot"`, never by a literal login: GraphQL strips the `[bot]` suffix, so Cursor's reviewer appears as `cursor` (and its security reviewer also as `cursor`), while REST callers see `cursor[bot]` — a literal `cursor[bot]` comparison MISSES the `cursor` thread and silently passes its findings (the makeMaxSpend false-Complete: an unresolved HIGH-severity `cursor` thread slipped a Complete because the gate matched only `cursor[bot]`). PREFER the shared `pr-address.sh fetch` (or `pr-land-comments.sh`), which already do this `__typename`-based bot detection — do not hand-roll the literal-login comparison. `reviewer-bots` in asana-config lists both Cursor logins (`cursor[bot]`, `cursor`) as a defensive fallback, but the `__typename == "Bot"` check is the primary. Never substitute `gh pr view`'s reviews/comments for the reviewThreads check. REVIEWER UNAVAILABLE IS NOT REVIEWER CLEAN, AND IS NOT A BLOCKER: when `watch-pr.sh` appends `reviewer-unavailable:<name>(<why>)` to its RESULT, that reviewer did not review the HEAD — either it posted no check-run at all, or it posted one and SKIPPED it, which is what running out of quota looks like. Both mean no review happened, which is a different thing from reviewed-and-found-nothing, so a `skipped` reviewer-bot check counts as coverage for NOTHING. Waiting cannot resolve either. Proceed to Complete, and record it in the report's Finalize Gate as an UNCHECKED box naming the reviewer and the reason, never as a checked reviewer-clean box. THAT BOX IS THE WHOLE RECORD: no Follow-ups & Risks item, no Testing-gap line, no completion-comment bullet, no PR comment, no "re-gate when quota returns" note, no narration in the session. Nothing can be done about a reviewer outage, so nothing else gets written (`require-clean-run-report.sh` and the Asana comment hook reject the extra mentions). NEUTRAL IS NOT CLEAN: `gh pr checks` buckets a reviewer-bot check-run conclusion of `NEUTRAL` as a non-failure, so the watch passes it — but `NEUTRAL` means the bot POSTED FINDINGS without hard-failing (Cursor Bugbot's neutral = "I found issues, non-blocking"). For a `reviewer-bots` author, "check-run completed-clean" means conclusion `SUCCESS` ONLY (a `skipped` conclusion from the REVIEWER ITSELF is the unavailable case above, not a clean one); a `NEUTRAL` conclusion, or a bot REVIEW in state `COMMENTED`/`CHANGES_REQUESTED`, means examine its findings and address/resolve them (cursor → `/bugbot`, others inline) before green — never treat the green `gh pr checks` exit as covering a reviewer bot. The unresolved-reviewThreads check above is the backstop that catches the findings; the NEUTRAL/COMMENTED state is the signal that triggers the examination. PRIMARY PR(s) means EVERY non-draft PR this run created or pushed to, in every repo — enumerate them explicitly before declaring green (e.g. the run's own PR list; `gh pr list --author @me` per touched repo as a cross-check) and gate on EACH. A PR created minutes before finalize (a second-repo PR, a late dep bump) is the one the gate exists to catch — gating only the first/oldest PR while a newer one's CI is still running is a completion-honesty violation. DRAFT dependency PRs (per `dep-pr-draft-vs-bump`) are EXCLUDED from the gate: a draft dep PR will fail CI/bugbot until its dep is published+bumped, so do NOT gate completion on it and do NOT run the reviewer-bot watch on it. Record each draft dep PR under the run report's **Follow-ups & Risks** as "un-draft + re-gate after `<dep>` publishes". The draft exclusion is for DEPENDENCY PRs ONLY — a PRIMARY PR (the run's actual deliverable) that is itself left in DRAFT can NEVER be green: reviewer bots do not run as check-runs on a draft, so a CI-only `watch-pr.sh` exit 0 covers CI alone and is NOT "every reviewer-bot completed-clean on HEAD." Treating a draft primary PR's CI-green as done — or dismissing its unresolved bot threads as "historical / commented, not check-runs" — is a completion-honesty violation. DRAFT-DURING-DEV IS PRESCRIBED (2026-07-31 bugbot credit gate): a primary PR now DEVELOPS as a draft (step 5 passes `--draft`; watch-loop pushes are bot-free) — that changes nothing here, because the gate binds at COMPLETE: the ready-flip (`gh pr ready <pr>`, step 6 phase 2) is a mandatory finalize step, the bots run on the flipped HEAD, and Complete still requires ready + every bot completed-clean + zero unresolved threads. The violation was never "PR was draft at some point"; it is and remains "Complete while draft / while bots never gated HEAD". To finalize a primary PR: mark it ready-for-review (`gh pr ready <pr>`) so the bots run on HEAD, then gate normally; unresolved reviewer-bot threads must be replied/resolved (`/bugbot` for `cursor[bot]`) before Complete, regardless of whether they predate this run. When green AND a task GID with an `agent_status` field exists → set `agent_status=Complete` (`~/.config/agent-watcher/update-status.sh <gid> Complete`). This is exactly what one-shot step 6→7 runs, AND what `/bugbot` runs when invoked standalone with a task GID (to finish a task manually after a blocker has been cleared). `/pr-address` NEVER sets Complete — it's a one-off and automated reviews can land after it finishes; completion belongs to whatever monitors continuously.</rule>
<rule id="yolo-stop-at-pr">In `--yolo` mode, NEVER merge the PR, tag a release, deploy, publish a package, or perform any other "land/ship" action. The agent's terminal action is reaching `agent_status = Complete` after the watch loop reports all-green. Merging is the human's decision. Force-pushing to the PR's own branch (to apply review/CI fixes) is allowed and expected. CARVE-OUT — a LAND/MERGE task: when the task's EXPLICIT deliverable is to land or merge an EXISTING PR (the task is about merging, not building a feature — signals: name/description like "land", "merge", "finish landing <X> PR", or it names a specific open PR to merge with no new code expected), the merge IS the deliverable, not a premature ship. Do NOT stop-at-PR and do NOT block on this rule; instead delegate to `/pr-land`, which by default enables GitHub auto-merge so the PR lands when CI is green (see pr-land). SECOND CARVE-OUT — landing an APPROVED feature PR at finalize-green, per `land-on-approval`. Everything else (a feature task with an unapproved PR and no Force Land field) still stops at PR. If genuinely ambiguous whether the task wants a merge, treat it as a normal feature task and stop at PR.</rule>
<rule id="yolo-no-silent-downgrade">Finalizing — opening a PR or setting `Complete` — while the prescribed in-app drive did NOT reach success is itself a CONCESSION (a DOWNGRADE), gated exactly like a formal block. The SAME gate (`require-completion-judgment.sh`) judges EVERY `/pr-create` and `update-status.sh Complete` — first segment or followup, wall or no wall — through the completion judge, whose J2 (testing depth and funding) and J5 (deferral validity, the concession taxonomy) dimensions catch a finalize whose latest attempt-log entry is a wall (`failed:`/`loss:`/`blocked:`), whose `/tmp/agent-test-blocker-<gid>.md` note exists, or whose attempt-log is simply EMPTY — i.e. you verified a weaker way, skipped the in-app drive, or bailed on a crash. A deny means the downgrade is NOT earned — do each failed item's `what_to_do` (apply the documented continue-workaround for a known gotcha like the Fabric `uiManagerDidDispatchCommand` SIGSEGV / maestro mis-targeting per the sim-testing playbook, swap-to-fund, build the missing harness) and reach the real success. The gated direct-verification fallback is legitimate ONLY with a GENUINE funded attempt logged (`log-attempt.sh` result `failed:`/`loss:`/`blocked:`) AND no remaining continue-workaround — this silent downgrade-to-fallback (the Xgram "stopped to avoid an accidental send" that never consulted the validator) is the exact bypass the gate exists to catch. Do not pre-empt the gate by skipping the attempt; ATTEMPT, log, then let the verdict rule. The judge also rules J1 asks-satisfied on every Complete: each ask in the task description and every operator comment since the report watermark must be delivered or explicitly surfaced with a logged attempt; a narrower delivery than asked (one token when "multiple" was asked) is a deny.</rule>
</rules>

<step id="7" name="Report (attach run report, then Complete)">
Build the run report and attach it, THEN mark Complete. Per `report-as-attachment`, this attachment (not comments) is how the run is documented.

0. Land + build routing FIRST (before the report, so the outcome is recorded in it):
   a. Landability per `land-on-approval`: check the PR for a human APPROVED review (`gh pr view <pr> --json reviews`) and run `~/.cursor/skills/asana-force-land.sh <gid>`. Landable → `/pr-land <task-url>` (task URL, never the bare PR), then skip (b).
   b. Not landing: cheese check per `cheese-build-on-green` — `~/.cursor/skills/asana-build-field.sh <gid>`; on a cheese value, run /cheese (`test-<value>` ← PR head, no dep pins). Then continue.
1. Copy `~/.cursor/skills/one-shot/templates/agent-run-report.md` to a scratch path named with BOTH the GID and the task short-name: `/tmp/agent-run-report-<gid>-<short-name>.md`. Fill the frontmatter — set `agent_session_uuid` from `$AGENT_SESSION_UUID` (the orchestration session that ran this), plus `outcome: complete`, `verified`, `verify_blockers`, repo/branch/pr, started/ended, `skills_used` — and every section. Use `_None observed._` for empty sections; keep it dense (bullets, signal over prose). Map content to sections:
   - phases that ran (`/asana-plan`, `/im`, `/pr-create`, `/build-and-test`) + watch-loop iteration counts → **Summary**.
   - the `/build-and-test` run as RUN EVIDENCE (do not leave thin — this is the visibility surface): the real action driven to terminal success (or the exact step it stopped at + why), method (static checks tsc/jest/eslint/verify-repo with results, sim build flavor, maestro flow path + MCP-explore vs yaml-proof, any `/debugger` use), environment (sim UDID/slot, roster account + any `env.json` switch, funding asset+amount + any swap-to-fund, provider forced + reverted), proof-screenshot paths + confirmation they are PR-attached, any gated direct-verification fallback, and what stayed unverified (mirror `verify_blockers`) → **Testing**. HACK-FORCED FRAMES ARE DECLARED, NOT BURIED: for every `HACKED`-named screenshot (build-and-test `hack-verify-visual-changes`), open the Testing section's screenshot list with a 🪓 line naming the file, the exact hack, that it was reverted with a clean `git status`, and what the frame does NOT prove (the trigger). A hack-forced frame listed like an organic one is a completion-honesty violation.
   - in `--yolo`, every auto-deferred decision (question, default chosen) → **Decisions** (flag only IRREVERSIBLE choices, per the template).
   - build/test/debug learnings → **Dev Notes & Gotchas** (inline-tagged). Harness friction → **Orchestration**. Skill defects → **Skill Gaps**.
2. Post the completion comment FIRST, per `report-as-attachment`'s exception-only spec (bulleted false positives / testing gaps / Force-Land note, or NO comment at all; reviewer-bot availability is never a bullet, per `finalize-gate`) — the attachment in step 2b sets the watermark, so a comment posted after it is lost to the next run's scope check.
2b. THEN attach the report: `asana-task-update.sh --task <gid> --attach-file /tmp/agent-run-report-<gid>-<short-name>.md --attach-name agent-run-report.md` (the attach gate renames it to `<N>-agent-run-report.md`). Skip both if no task GID (ad-hoc task) and report in chat only.
3. Set the `tested` field to the method(s) actually performed (per `set-tested-field`): `~/.config/agent-watcher/set-tested.sh <gid> <Option ...>`.
4. Set agent_status=Complete — ONLY after `finalize-gate` reports all-green.
5. Return a short chat summary + PR URL + phases ran.

Per `report-as-attachment`, the run-report doc is attached at `Complete` — including a blocked completion, which attaches it like any other `Complete` with the blocker named (one-line blocker comment first, then the attachment).
</step>
