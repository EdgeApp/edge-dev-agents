Governs the plan and implementation phases of `/one-shot` (`agent_status = Planning`, then `Developing`); the core step map row `2-3. Plan and implementation` points here.

<rules description="Non-negotiable constraints, binding exactly as if written in the core SKILL.md.">
<rule id="im-owns-implementation">Step-3 implementation is governed by /im's contract EVEN when executed inline per `yolo-execution`: BEFORE the first code edit, read `~/.cursor/skills/im/SKILL.md` and follow it. Concretely: every commit goes through `~/.cursor/skills/lint-commit.sh` — raw `git commit` is FORBIDDEN, and `git commit --no-verify` doubly so (a failing hook/script is a halt-on-error STOP per `no-script-bypass`, not something to bypass); run `lint-warnings.sh` before the first `.ts`/`.tsx` edit; CHANGELOG entry only in the last commit. GATE before step 5: do not invoke `/pr-create` until you confirm this run actually read im's SKILL.md and produced every commit via lint-commit.sh — if it didn't, stop and redo the commits through /im first.</rule>
<rule id="multi-repo-subtasks">When this run produced PRs across MORE THAN ONE repo, do NOT attach them flat onto the main task: run `/pr-create` with `--no-asana-attach`, then create a SUBTASK PER PR and attach each PR to its own subtask — one `asana-task-update.sh --create-subtask ... --attach-pr ...` call per PR (flag syntax: /asana-task-update). The main task stays the umbrella (run-report only). Single-repo runs attach their one PR directly per `attach-prs-by-default`. Dependency PRs differ per `dep-pr-draft-vs-bump`.</rule>
<rule id="dep-pr-draft-vs-bump">WHAT QUALIFIES as a draftable dependency PR (read this first — mis-classifying the task's OWN deliverable as a dep PR drafted it out of the gate and produced a false Complete): a dependency PR lives in a DIFFERENT repo than the task's primary deliverable AND is drafted ONLY because it cannot pass CI until ITS dep publishes. NOTE since 2026-07-31: draft state alone no longer signals dep-blocked — PRIMARY PRs also develop as drafts (the bugbot credit gate, step 5) — so classify by this rule's qualifying test, never by draft state: a primary PR's draft ends at the finalize ready-flip; a dep PR's draft ends when its dep publishes. The task's actual deliverable PR — and ANY PR that passes CI standalone (including a self-contained PR in a dep-family repo like edge-info-server when THAT repo IS the deliverable) — is a PRIMARY PR: gate it normally per `finalize-gate`, never `--draft` it to dodge the gate. "It's in a dep-ish repo" does NOT make a PR draftable; "it can't go green until another package publishes" is the only test. For a dependency change the feature needs (the gui needs updated `edge-core-js`/`edge-currency-accountbased`/etc.), build the subtask even though the dep isn't published yet: (a) if the dep PR has changes BEYOND a version bump (real code), open it as a DRAFT (`gh pr create --draft`), create its subtask, and attach it — it will fail CI until the dep publishes, which is expected; (b) if the change is ONLY a dependency version bump, a task comment on the subtask suffices and NO PR is needed, but still CREATE the placeholder subtask so the multi-repo scope is visible. Draft dep PRs are excluded from the completion gate (see `finalize-gate`).</rule>
<rule id="tdd-when-flagged">Resolve the task's TDD field at EVERY segment start — during planning on a fresh run, and again on every re-engagement (a followup skips planning, and the operator flips this field precisely to commission a TDD for work that already shipped): `~/.cursor/skills/asana-field-value.sh <task-gid> "TDD?"`. A flip from `none` to `tdd` on an already-implemented task means the TDD is owed NOW and is written from the IMPLEMENTED state (tdd `post-impl-retro` shape: what was built, why, what was rejected), not as a pre-implementation draft; the re-arm itself is the authorization, so no interactive gate. When it prints `tdd`: follow `/tdd`, which writes the doc FROM WHAT WAS BUILT (tdd `write-after-building`) — so the initial doc comes after at least one implementation turn, never as a pre-implementation sketch — and ALWAYS lives COMMITTED at `src/docs/<slug>.md`, never a gist: a set TDD field is the top of tdd `output-target`'s precedence, so it outranks even the non-owner-PR rule (commit to the task's own branch, opening one if the task has none). Hands-off runs skip tdd's interactive `draft-gate` ask (the flagged task IS the authorization) but keep its fetch-before-update requirement. Post the doc link as an Asana comment. EVERY LATER TURN updates it: body rewritten to the current implementation, that phase's entry appended to the single `## Phase history` section (tdd `current-state-body-phases-in-one-section`) — the body never becomes a changelog. The doc RIDES IN THE BRANCH'S FIRST COMMIT (tdd `doc-rides-the-first-commit`): stamp it, then `lint-commit.sh --fixup <first-commit>`; a standalone doc commit or an "update the design doc" commit is a squiggly-path finding, and the Complete gate checks the stamp against HEAD's code tree. After implementation and testing pass, fold in the retrospective per tdd `post-impl-retro`. When the field prints `none`, no TDD work is owed.</rule>
</rules>

<step id="2" name="Plan/context phase">
Set agent_status=Planning (see `agent-status-on-pending-task`). Then run `/asana-plan` with the provided input mode:

- Asana URL mode: fetch task context and create plan
- Text/file mode: create plan from provided requirements

If `--yolo` is active, do NOT wait for user confirmation — accept the plan and move to step 3 immediately. Otherwise wait for user confirmation handled by `/asana-plan`.
</step>

<step id="3" name="Implementation phase">
First provision the workspace (per **Per-task worktrees** in `references/intake.md`): from the plan, create a co-located worktree for the target repo — plus any gui-dependency repos the task modifies, then `updot`-link them into the gui worktree — and `cd` into the primary repo's worktree. (Skip on manual non-watcher runs already inside a normal checkout.) Before setting agent_status=Developing, the plan file `plan-<gid>-<short-slug>.md` (asana-plan `create-plan-required`) must already exist and be attached via `asana-task-update.sh --attach-file`; a followup segment skips this. Then set agent_status=Developing and run `/im` using the approved `/asana-plan` output.
</step>
